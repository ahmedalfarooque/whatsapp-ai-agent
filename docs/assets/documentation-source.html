PART 1

Understanding the Project

What this system is, how the pieces connect, and what happens from the moment a customer types a message.

1. Executive Summary

What is this project?

The WhatsApp AI Agent is a computer program that lets a business talk to its customers on WhatsApp automatically. A customer sends a normal WhatsApp message, and this program reads it, thinks about it using an AI model, remembers earlier parts of the conversation, answers questions using the business's own information, and — if the customer wants — checks a real calendar and books a real appointment. All of this happens without a human typing the reply.

What problem does it solve?

Many small businesses cannot answer every WhatsApp message instantly, especially outside office hours. Customers ask the same questions repeatedly ("what do you charge?", "are you open Saturday?", "can I book Tuesday at 3?"). This project answers those automatically, using only facts the business owner has approved, and hands off to a human when it doesn't know something.

What happens when a customer sends a message?

EXAMPLE

Customer sends: "Hello, I want to book an appointment tomorrow."

Customer types a message in WhatsApp

↓

↓

↓

↓

↓

↓
Google Calendar (only if a tool was needed)
↓

↓
WhatsApp sends it back to the customer

The Smart Receptionist analogy

EXPLAIN LIKE I'M 10

Imagine this whole system is a smart receptionist working at a front desk:

  • WhatsApp = the telephone the customer calls on
  • AI (OpenRouter) = the receptionist's brain, doing the thinking
  • SQLite = the notebook where the receptionist writes down who called and what was said
  • Google Calendar = the appointment diary on the desk
  • Webhook = the doorbell that tells the receptionist "someone is here!"
  • Knowledge files = the instruction binder listing prices, services and rules
  • Docker = the box that lets the whole desk be moved to any building and still work the same way
  • Caddy = the security guard at the door who checks IDs (HTTPS) before anyone gets in
FOR THE TECHNICAL READER

This is a Node.js/TypeScript Express server that receives Meta WhatsApp Cloud API webhook events, resolves a customer by their WhatsApp number, loads/persists conversation state in SQLite, builds an OpenRouter chat-completion request with a tool-calling loop (check_availability, book_appointment), and calls the Google Calendar API (service account auth) for real availability and booking. It runs as a Docker container behind Caddy for automatic HTTPS, intended for a single VPS.

3. Every Connection Explained

A. Customer → WhatsApp

The customer opens WhatsApp on their phone and types "Hi". WhatsApp packages this as a message and sends it to Meta's servers over the internet — nothing our code does yet; this step happens entirely inside the WhatsApp app and Meta's network.

B. WhatsApp → Meta Cloud API

Meta owns WhatsApp and runs the "Cloud API" — a set of servers that receive every message sent to a business's WhatsApp number and can send messages back on the business's behalf. Our application never talks to the customer's phone directly; it always talks to Meta, and Meta relays the message.

C. Meta → Webhook (POST /webhook)

WHAT IS A WEBHOOK?

A webhook is like a doorbell. Instead of our program constantly walking to the door and asking "did anyone arrive yet?" (which wastes effort), we give Meta our doorbell number (a URL) and Meta rings it themselves the instant a new message shows up. Our code (src/webhook/router.ts) is always listening for that ring.

Real endpoint in this project: POST https://<your-domain>/webhook, implemented in src/webhook/router.ts.

D. Webhook Security

LayerPurposeSource file
GET verification (one-time handshake)When you first register the webhook URL with Meta, Meta sends a GET request with a secret hub.verify_token. We check it matches our own WHATSAPP_VERIFY_TOKEN before confirming.src/webhook/verifyToken.ts
POST signature (every single message)Meta signs every webhook POST with X-Hub-Signature-256, computed from the exact request body and our META_APP_SECRET. We recompute the same signature and compare.src/webhook/verifySignature.ts
Timing-safe comparisonWe compare signatures with crypto.timingSafeEqual, not ===, so an attacker can't guess the correct signature one character at a time by measuring how fast the comparison fails.same file
WHY THIS MATTERS

Without this check, anyone on the internet could send a fake message to our webhook pretending to be a real customer — for example, pretending someone confirmed a booking they never made. The signature proves the message truly came from Meta.

E. Node.js / Express — the central controller

Express is the framework that receives every HTTP request and decides which piece of code should handle it. In this project, it's the single front door: it applies security headers (Helmet), logging, rate limiting, and JSON parsing, then routes /health, /readiness, and /webhook to their handlers. It's "central" because every request — and only requests that came in this way — reach the rest of the system.

F. SQLite — where the receptionist writes things down

SQLite is a database that lives in a single file (data/app.db) rather than a separate server. This project stores:

  • customers — one row per WhatsApp number that has ever messaged
  • conversations — a "session" of memory for a customer; a new one starts on restart
  • conversation_messages — every message, in order, so the AI has real context
  • booking_sessions — partial booking details being collected across turns
  • webhook_events — Meta's message IDs, so the same message is never processed twice

See Chapter 8 for the full schema diagram and an explanation of every table.

G. Knowledge files — the instruction binder

knowledge/ ├── business.md ├── services.md ├── policies.md ├── faq.md └── booking.json

These are plain Markdown/JSON files, loaded once at startup by src/knowledge/loader.ts and pasted into the AI's system prompt. Business facts (prices, hours, policies) live here — not hard-coded in the TypeScript source — so a non-developer can edit a text file to change what the AI says, without touching code. The system prompt (src/llm/buildSystemPrompt.ts) explicitly instructs the AI to answer only from these files and never invent facts.

PLANNED / NOT YET CONFIGURED

The knowledge files shipped in this repository contain example/placeholder content only (clearly marked as such inside each file). They must be replaced with the real business's information before going live — see Chapter 18.

I. Tool calling — the receptionist's special abilities

RECEPTIONIST ANALOGY

A good receptionist doesn't just talk — sometimes they need to walk over to the appointment diary and actually check it. "Tool calling" is the AI doing exactly that: it can pause mid-thought and say "I need to actually look this up," run a real function in our code, get a real answer back, and then continue.

Why check availability twice? Between the moment the AI shows a customer a free slot and the moment they say "yes, book it," a few seconds (or longer) pass. In that window, someone else could book that exact slot. src/calendar/booking.ts re-queries Google Calendar's free/busy data immediately before creating the event, and only proceeds if the slot is still free — this closes that race window instead of trusting a stale answer.

K. Docker

EXPLAIN LIKE I'M 10

Imagine packing the entire application — the code, the exact version of Node.js it needs, all its tools — into one sealed box. Wherever you ship that box (any computer, any VPS), it opens up and runs exactly the same way. That box is called a container, and Docker is the tool that builds and runs it.

Internet

Caddy is a web server placed in front of the application. Its job in docker-compose.yml/nginx/Caddyfile is to automatically obtain and renew a free HTTPS certificate (via Let's Encrypt) for the domain configured in DOMAIN, and forward traffic to the app container over plain HTTP internally. Meta refuses to send webhooks to a non-HTTPS URL, so this step is required before the webhook can be registered.

4. Message Lifecycle — Step by Step

Every single inbound WhatsApp message goes through exactly this sequence (source: src/webhook/router.ts + src/pipeline/processInboundMessage.ts):

#StepIn simple words
1Customer sends a messageThey type in WhatsApp and hit send.
2Meta receives itMeta's servers get the message first.
3Meta calls our webhookMeta rings our doorbell with the message attached.
4Server verifies the requestWe check the signature is really from Meta.
5Server replies 200 OK immediatelyWe tell Meta "got it" right away, before doing any AI work, so Meta doesn't think we're broken and retry.
6Message ID is checkedHave we seen this exact message before?
7Duplicate messages are ignoredIf yes — stop here, do nothing else.
8Customer is identified by wa_idTheir WhatsApp number becomes their ID automatically.
9Customer lock is acquiredMake sure no other message from this same customer runs at the same time.
10Conversation is loadedPull up their notebook page from SQLite.
11Restart command checkedDid they just say "restart" or "reset"?
12Knowledge is usedBusiness facts are added to what the AI can see.
13AI receives full contextSystem instructions + history + knowledge, sent to OpenRouter.
14AI answers OR requests a toolEither a plain reply, or "let me check the calendar first."
15Tool executesOur code actually calls Google Calendar (if needed).
16Tool result goes back to the AIThe AI sees the real answer, not a guess.
17AI generates the final responseNow it writes the message the customer will actually see.
18WhatsApp API sends the responseOur code calls Meta's API to deliver the reply.
19Conversation is storedEvery turn is saved to SQLite for next time.
20Lock releasedThe next message from this customer (or anyone) can now be processed.
SOURCE MAPPING

Steps 4–7 → src/webhook/router.ts. Steps 8–11 → src/pipeline/processInboundMessage.ts + src/restart/isRestartCommand.ts. Steps 12–17 → src/llm/agentLoop.ts + src/tools/*. Step 18 → src/whatsapp/client.ts. Steps 19–20 → src/memory/conversationRepo.ts + src/pipeline/idempotency.ts.

5. Real Conversation Examples

These examples reflect the actual behavior verified by the test suite (tests/integration/conversationFlow.e2e.test.ts), not hypothetical behavior.

Example 1 — First contact

Customer: "Hi"
Agent: "Hello! How can I help you today?"

A brand-new customer is automatically created in the customers table using their WhatsApp number — no signup form, no manual step.

Example 2 — Question answered from knowledge

Customer: "What services do you provide?"
Agent: answers using only what's written in knowledge/services.md — it cannot invent a service that isn't listed there.

Example 3 — Checking availability

Customer: "I want an appointment tomorrow."
AI
→
check_availability
→
Google Calendar
→
real free slots
→
AI's reply

Example 4 — Booking it

Customer: "Book it for me."
AI
→
book_appointment
→
re-check
→
create event
→
confirmation

The agent never says "you're booked" unless book_appointment actually returned success.

Example 5 — Two messages arrive together

If the same customer sends two messages almost simultaneously (or Meta redelivers one while the first is still processing), withCustomerLock (src/pipeline/idempotency.ts) makes the second one wait until the first fully finishes — they are processed one at a time, in order, never in parallel. This is proven by the concurrency test in tests/integration/conversationFlow.e2e.test.ts, which fires three simultaneous messages and confirms all three land in the database without corruption.

Example 6 — Duplicate delivery

If Meta delivers the exact same message ID twice (a normal retry behavior on their side), src/memory/webhookEventRepo.ts's INSERT OR IGNORE means the second attempt is recognized as already-seen and silently skipped — no second AI call, no second reply.

Example 7 — "restart"

Customer: "restart"
Agent: "Done — I've started a fresh conversation. How can I help you?"

The current conversation row is marked ended, any in-progress booking session is cleared, and a brand-new conversation begins — but nothing is deleted; the old conversation and its messages remain in the database for history/audit.

Example 8 — AI or provider failure

If OpenRouter (or any step in the agent loop) throws an error, the customer is never shown a stack trace or technical detail. They receive a plain, safe message ("Sorry, something went wrong on our end...") while the real error is logged internally for the developer to see.

Every layer exists to stop a different kind of attacker: HTTPS stops eavesdropping, the signature stops impersonation, rate limiting stops flooding, and validation stops malformed/malicious payloads reaching business logic.

ProtectionSimple explanationTechnical detail

Rate limitingStops one source from flooding the doorbell.express-rate-limit, RATE_LIMIT_PER_MINUTE (default 120/min) on /webhook.

Secret redaction in logsKeys and tokens never appear in log files.src/logger.ts pino redact config masks Authorization, signature headers, and any field named token/key/secret.

Malformed JSON handlingA broken message doesn't crash the server.Central error handler returns 400 invalid_json, not a raw 500.

Environment variables / .envSecrets never live in the code..env is gitignored; all secrets loaded via process.env, validated at startup by src/config/env.ts.

8. The Database (SQLite Memory)

NOTEBOOK ANALOGY

Think of the database as the receptionist's notebook. Every page is one type of record: one section for "who has called before," one for "what did we talk about," one for "appointments being arranged," and one for "messages we've already dealt with, so we don't answer them twice."

Schema diagram (actual tables, from src/memory/migrations/001_init.sql)

customers (id, wa_id UNIQUE, display_name)
↓ 1-to-many
conversations (id, customer_id, status, started_at, ended_at)
↓ 1-to-many       ↓ 1-to-1
conversation_messages
(conversation_id, role, content, tool_call_id, tool_name, whatsapp_message_id, direction, created_at)
booking_sessions
(conversation_id UNIQUE, status, service_type, preferred_date, preferred_time, duration_minutes, customer_name, calendar_event_id)
webhook_events (independent table)
(message_id PRIMARY KEY, received_at, processed_at, error)

Table-by-table explanation

TablePurposeWhy it exists
customersOne row per WhatsApp number that has ever messaged.Gives every customer a stable identity without any signup — the phone number is the identity.
conversationsOne row per "session" of memory. status is active or ended.Lets "restart" cleanly start a new memory session without deleting the old one — a customer can have many conversations over time, but only one active at once.
conversation_messagesEvery user/assistant/tool message, in order.This is what actually gets sent back to the AI as "conversation history" on the next turn — it's the AI's real memory.
booking_sessionsPartial appointment details (service, date, time, name) collected across several messages.A booking often can't be completed in one message; this lets the system remember "we already know the service and date, we just need the time" between turns.
webhook_eventsEvery WhatsApp message ID Meta has sent us.The primary key is the message ID itself, with INSERT OR IGNORE — this is the exact mechanism that makes duplicate delivery impossible to process twice.

Persistence & duplicate protection

  • The database is a single file (data/app.db), stored outside the Docker container on the VPS disk (a bind-mounted volume) — restarting or rebuilding the container does not lose data.
  • PRAGMA journal_mode = WAL and PRAGMA foreign_keys = ON are set at connection time (src/memory/db.ts) for durability and referential integrity.
  • Restart ("reset") never deletes rows — it flips conversations.status to ended and starts a new row. Nothing is destroyed.

The bounded tool loop

The loop in src/llm/agentLoop.ts can repeat — the AI can call a tool, look at the result, and decide it needs to call another tool before answering. To stop this from running forever (a malfunctioning model looping endlessly, burning cost), the loop is capped at MAX_TOOL_ROUNDS, which defaults to 4 (confirmed in src/config/env.ts). If the cap is reached without a final plain-text answer, the loop returns a safe fallback message ("I need a moment to look into that properly...") rather than leaving the customer without any reply.

Safe fallback behavior

  • Unknown tool name requested by the model → returns a structured error to the model, not a crash.
  • Malformed tool-call JSON arguments → parsed defensively; falls back to an empty object rather than throwing.
  • A tool handler throws an exception → caught, logged, and reported back to the model as {"error":"tool_execution_failed"} so the conversation can continue.
  • OpenRouter itself is unreachable/errors → caught one level up in the pipeline; customer gets the generic error reply (Chapter 7).

All of this is exercised by tests/unit/llm/agentLoop.test.ts with a mocked OpenRouter client.

What happens if the slot becomes unavailable?

If the re-check (immediately before events.insert) finds the slot is no longer free, src/calendar/booking.ts returns {"success": false, "conflict": true} instead of creating anything. The AI is instructed (system prompt) to apologize and offer alternative times rather than claiming success — it is structurally impossible for the code to report a booking succeeded when Google Calendar didn't actually confirm it.

Google Calendar access requirements

  • A Google Cloud service account is used (server-to-server auth, no interactive login).
  • The target calendar must be explicitly shared with that service account's email, with "Make changes to events" permission — otherwise every calendar call will fail with a permissions error.
  • Availability is computed via freebusy.query (the current, non-deprecated Calendar API v3 endpoint) — see src/calendar/availability.ts.
REQUIRES CONFIGURATION

The calendar integration is fully implemented and unit-tested with a mocked Google API, but it has not been exercised against a real Google Calendar in this environment — that requires real GOOGLE_CLIENT_EMAIL/GOOGLE_PRIVATE_KEY/GOOGLE_CALENDAR_ID credentials, which were not available during development.

Common questions

"What happens if I change my opening hours in business.md?"

The text the AI talks about updates immediately after a restart/redeploy — but the actual booking math (which hours count as available) is driven separately by the BUSINESS_HOURS_START/_END environment variables, not by this file. Change both together, or the AI's description and the real calendar behavior will disagree.

"What happens if I add a new service to services.md?"

The AI can immediately describe and quote it after the next restart (knowledge files are loaded once at boot, per src/knowledge/loader.ts) — no code change needed. There is no code-level list of "valid services"; the AI relies entirely on this file.

"What happens if I change a policy?"

Same as above — edit policies.md, restart/redeploy the app, and the new wording is what the AI will use going forward.

RESTART REQUIRED

Because knowledge files are only read once at process startup, any edit requires restarting the app (or a fresh deploy) to take effect — simply saving the file while the app is already running has no immediate effect.
